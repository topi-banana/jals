# Build script example

This project runs `build.java` before `javac`. The script uses only JALS's storage-backed API to
generate `target/jals/build/script/out/generated/BuildInfo.java`, adds it as a source, and
contributes compiler/JVM flags and subprocess environment entries.

## Run it

From this directory:

```sh
cargo run -p jals-cli -- run
```

With `jals` installed, use `jals run`. The program prints:

```text
generated by build.java
java
java
```

`jals build --dry-run` still runs the script so the displayed `javac` command includes its generated
source and `-Xlint:all`. It publishes managed output and cache state under `target/jals`, but it
does not run `javac` and does not apply exclusive source-tree publications — a preview never
rewrites or deletes anything outside `target/jals`. `jals clean` removes `target/classes` and
`target/jals/build`, including generated script output.

## What it demonstrates

- `[build] script = { type = "java", file = "build.java" }` enables the optional pre-build phase.
- `Project.exists` reads the immutable project snapshot; `Output.writeText` can publish only below
  `target/jals/build/script/out`.
- `Build.addSource`, `addJavacArg`, `addJvmArg`, `setCompileEnv`, and `setRunEnv` augment the later
  compile/run requests.
- `rerunIfChanged` and `rerunIfEnvChanged` narrow cache invalidation to declared inputs.
- `Build.warning` reports a non-fatal diagnostic, while `Build.error` prevents all pending output
  from being published. `Build.metadata` records host-readable key/value data without changing
  `javac` or `java`.

See [`jals-build/README.md`](../../jals-build/README.md#java-build-scripts) for the complete API and
sandbox/cache behavior.
